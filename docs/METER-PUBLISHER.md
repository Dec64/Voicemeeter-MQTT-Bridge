# Bounded v2 MQTT publisher

`MeterTelemetryPublisher` consumes independent fast/slow queues on an already connected `IMqttClient`. It is not instantiated by `BridgeService` and never connects, reconnects, subscribes, discovers entities or starts the sampler. Live v2 stays disabled.

Each enabled stream has one sequential consumer and at most one in-flight send. The sampler can still replace its one pending snapshot while a send stalls. The streams share one builder/session and a short serialization lock; they never hold that lock while awaiting MQTT. The caller gives the publisher exclusive ownership of frame-building calls on that builder. Metadata built from the same builder has the matching session ID. Track sequence per topic: serialization shares a counter, but send completion across the two topics can occur in a different order.

The publisher checks global/per-stream flags, validates settings and requires each enabled stream's age budget to exceed its configured window. Fast and slow cannot consume the same queue. `ReadFreshAsync` removes expired/untracked snapshots, and freshness is rechecked inside serialization and after formatting before transport submission. Publication UTC is assigned during formatting, never at enqueue. Serialization can consume a sequence number even if the final age check drops the frame. A send already handed to MQTT cannot be recalled or guaranteed fresh at arrival; this is not a latency guarantee.

Messages use the supplied expanded base topic unchanged, adding `/v2/meters/fast` or `/v2/meters/slow`. Both are non-retained QoS 0. Fast JSON stays unchanged. Slow JSON uses `window_ms` and adds per-source `sensor_tap`: `pre` for strips when configured, otherwise the first configured input tap, and `output` for buses. Sensor consumers must select that explicit field's matching level, preserve unavailable/null values, and must not silently claim post-mute readings are pre-fader. Slow discovery is not implemented in this slice.

An exception, disconnected client observed before a send, or unsuccessful publish result faults the session and cancels its other reader/send. There is no retry of the failed frame. Normal queue completion ends that stream; caller cancellation ends both streams normally. All actual send tasks are awaited, with the cancellation token passed through. If a client ignores cancellation, shutdown remains pending rather than abandoning a send and starting more work. Transport deadlines/connection supervision still need integration and real-client verification.

The producer owns queue completion; the publisher does not close queues or disconnect/dispose the shared client. [MeterTelemetrySupervisor](METER-SUPERVISOR.md) now coordinates the sampler/publisher pair, cancels sampling immediately on publication failure, and awaits old work before allowing a fresh run. One publisher instance can run only once. The host still owns connection events and explicit restarts; cancellation/session identity must also gate real HA consumers so old connection data is not reused.

The tests use in-memory snapshots and a strict mock MQTT client. No native DLL, broker, HA or live configuration was accessed. Remaining work includes connection-event integration, retained metadata/status/discovery, standard sensor availability, actual source assignments and SDK validation, HA benchmarks, and the modular HACS card/editor/shared subscription.
